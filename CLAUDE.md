# Pixeltrunk

AI-powered photo archive for professional photographers. Sister product to SimplePhotoShare (spsv2).

Generic workflow, shipping, collaboration, and design rules are **global** (`~/.claude/CLAUDE.md` + `~/.claude/rules/`). This file is Pixeltrunk business logic only.

## Quick Reference

- **Stack:** Next.js 15, React 19, TypeScript, Tailwind CSS 4, Supabase (pgvector), Cloudflare R2, Modal GPU, Inngest
- **Docs:** `docs/PRD.md` (product), `docs/TECHNICAL.md` (technical), `docs/OPS.md` (alpha access, metering, /ops, crons — read before touching auth/ops/usage), `docs/SESSION-HANDOFF.md` (handoff prompt)
- **Brand:** Elephant pixel-mosaic logo, Libre Baskerville wordmark, Playfair Display headlines, Inter body, stone/white palette with emerald accent

## Key Patterns

- Presigned URL uploads (client -> R2 direct)
- AI processing via Modal serverless GPU
- pgvector for CLIP semantic search
- Smart Stacks group similar images, surface best shot
- AI suite (FULL DOC: `docs/AI.md` — read it before touching anything AI): SigLIP-2 semantic search (archive/editor/guest/selfie), face clustering + People view + identity-suggestion engine, scene sections + smart sections, group focal points. Settlement-triggered Inngest lanes, kill switch `AI_INDEXING_ENABLED`. Two invariants: AI writes ONLY its own columns (never `processing_status` or anything display reads), and AI suggests — humans apply. Modal CLI: `~/.venvs/modal-cli/bin/modal`
- Cover types (image/mosaic/solid/crossfade) — `src/lib/cover/*`; `normalizeCoverSettings()` is the single parse point; email/OG raster composes ONLY in the Inngest `cover-raster` job (pool.ts stays sharp-free for routes)
- **SPS import is a PULL that moves bytes** (built 2026-08-11; contract `tasks/sps-archive-pull-spec.md`, build notes `tasks/sps-pull-build-plan.md`). Pixeltrunk pulls; SPS never pushes. The old zero-copy push lane (`import.ts`, `POST /api/sps/import`, `event/imported`) is DELETED — it minted rows pointing at SPS's R2 keys on the false premise of a shared bucket (SPS serves `pub-7363d57d….r2.dev`, the archive stores `sps-prism`), so every row it made was a tile this app could not read. The lane now: `pull-client.ts` (protocol) → `pull-event.ts` (byte mover) → Inngest `sps-pull` → review UI at `/events/import`. Four invariants: **bytes land before the row exists** (no ghost-tile window at all — the inverse of the upload path, which must pre-create rows to presign); the walk is driven by **manifest page**, so signed URLs are always seconds old and `sps_pull_jobs.next_offset` is the resume point; completion is **the absence of `nextOffset`**, never a count (`imageCount` includes AI copies the manifest excludes); and `POST /pulled` fires **only after durable write**, because that call is what lets SPS delete its copy. Per-photo provenance lives on `images.sps_image_id / sps_quality / sps_pulled_at` with a unique index on `(event_id, sps_image_id)` — that index, not the importer's care, is what makes a resumed job idempotent. Verify with `npx tsx scripts/verify-sps-pull.ts <eventId>` (sha256 round-trip; inspection is not evidence here — that is how the lossy-source claim survived for months).
- **The SPS connection token is a stored plaintext credential, one row per user** (`sps_connections`, service-role only, RLS on with no policies). NOT an env var: SPS mints per `user_id`, so an env var pins the whole install to one SPS account. Note the asymmetry — SPS only *verifies* the token so it keeps a hash; Pixeltrunk must *present* it on every request so it must keep the plaintext. `getSpsToken()` in `connection.ts` is the only reader; it never reaches the browser, a log line, a `system_errors` blob, or an argv. Paste screen: `/settings/connections`, which validates against `GET /events` before storing (SPS shows the token once, so a truncated paste has to fail at the paste). Minting on the SPS side is gated behind `NEXT_PUBLIC_ENABLE_PIXELTRUNK`.
- **`/api/sps` is NO LONGER public in middleware** (2026-08-11) — only `/api/sps/enhancements`, the one route SPS calls server-side with no session. The old blanket rule dated from the push lane and would have left any new `/api/sps/*` route reachable without a session.
- **CORRECTED 2026-08-11: SPS is NOT a lossy source.** This file previously said "SPS re-compresses on ingest (~⅓ the bytes at identical dimensions), so it is a lossy source." That was measured honestly on FoU26 frames but generalized from *stored bytes* to *current behaviour*, and it is wrong: SPS `f406ee7` (2026-05-05) added a passthrough branch to `processImage`, so a JPEG upload with no test-mode watermark and no branding overlay is stored **byte-for-byte** as `original.jpg`. Verified by sha256 round-trip — a 3,583,248-byte camera JPEG comes back identical. The FoU26 frames predate the fix. SPS's `IMAGE_SIZES` still reads `quality: 95` because that encoder still runs for the excluded cases (watermarked/test events, branded events, HEIC/PNG/WebP), which is why reading the config alone gives the wrong answer. SPS now exposes a pull API that reports per-image `quality: 'archive' | 'lossy'` so this never has to be inferred again — spec in `tasks/sps-archive-pull-spec.md`.

## Hard-won gotchas (full log: `tasks/lessons.md` — skim it before touching API routes)

- **`getAuthUser()` hands back the SERVICE client, which bypasses RLS.** Every query in every route it feeds must carry an ownership filter (`.eq("user_id", ...)` or `events!inner(user_id)` join). This exact omission shipped as an IDOR twice (lessons #2 and #14) — when touching an API file, scan its siblings for the same hole.
- **Never run `npm run build` while a dev server is up *in the same working directory*** — they share `.next` and the build corrupts the running server (has bitten three separate times). `main` auto-deploys to Vercel, so `next build` (not just tsc) must pass before every commit. **A git worktree is a different working directory and has its own `.next`**, so building in `.claude/worktrees/<name>/` is safe while a dev server runs in the main checkout — the test is the process's cwd, not the port. Confirm with `lsof -p <pid> -a -d cwd -Fn`, and run that check as its own command: batching it into the same invocation as the build means you read the answer after the build has already run.
- **The repo lives in iCloud-synced ~/Documents.** Sync races drop conflict copies (`file 2.ts`) inside `.next` → phantom duplicate-identifier tsc errors. tsconfig excludes them; if a ` N.ts` file errors, it's iCloud, not the code. Edits can also silently fail to apply — verify Edits landed before building.
- **Upsert `onConflict` must exactly match a LIVE unique constraint** — check `pg_constraint` on the live DB, not the migration file. Optimistic UI masks failed writes; guest favorites 500'd for months unseen.
- **Streaming routes need `maxDuration`, parallel prefetch, and real backpressure** — the ZIP export shipped corrupt 1.6GB files when Vercel killed a sequential-fetch stream at the 300s default. `store: true` for JPEG zips.
- **DATE columns format with `timeZone: "UTC"`**; timestamps format local.
- **Every progress number must be the thing the user handed over.** The upload total used to EXCLUDE duplicates and failures so the ring could close at 100%, so it shrank while running (1,106 → 1,090 in front of Justin, 2026-08-11). The denominator is now `files dropped`, unchanging; each file reaches one terminal state (uploaded / linked / duplicate / failed) and every subtraction is NAMED on screen, never silently deducted. Same rule killed three other lies the same day: the banner reporting the presign-ahead window as "still uploading" (it counts down while hundreds wait), "Confirmed 0" on a perfect SPS import (reported ≠ released), and the section sidebar rendering a mid-write snapshot as final. **If a count can only be produced from internal machinery, it is not the count to show** — the client knows what was dropped, the rows know what landed; prefer those.
- **The duplicate guard is SECTION-aware, and "already in the event" means LINK, not skip.** `section_images` is a link table, so one image can live in several sections. Uploading a file already in the event but not in the target section adds the link (one image, no second copy, status `linked`); only a same-section collision is a true duplicate, and that one stops and offers replace-or-skip with the colliding image id so Replace has something to delete. `linked` must NEVER share the `duplicate` status: that status feeds the replace panel, where Replace deletes the original to re-upload an identical copy. Section-scoped DELETE is the mirror image and has one home, `partitionSectionDelete()` — member here plus a membership anywhere else (including other events and website sections) unlinks; last copy hard-deletes; a hard delete out of a locked section is blocked all-or-nothing.
- **AI-dependent controls are DISABLED WITH A REASON, never hidden.** A control that vanishes teaches nothing and leaves people hunting; a greyed one carrying "available in about 18 minutes" explains itself and points at what works now. Four of five sorting modes (`letter`, `per-person`, `even`, `full-set`) are pure filename planners needing NO AI — only `scenes` and Smart section need embeddings, and per-person is what a headshot day wants. AI indexing debounces **2 minutes** per event (not 15 — see `docs/AI.md`), and the banner forecasts duration at ~54 photos/min until a measured rate exists.
- **Never call a React state setter from a high-frequency event — and a clean server log during a "stuck" client means LIVELOCK, not deadlock** (lesson 92). `updateFile` used to `setBatches` on every XHR progress tick (~50ms per request × 12 workers ≈ 240/sec), and each write re-mapped every batch AND every file in the target batch: **cost per tick was O(total files staged)**. A rapid-fire drop from several folders (~36 batches, ~2,600 files) meant ~3M allocations/sec, and the main thread starved — uploads fell to 0.2 Mbps, and a section create that SUCCEEDED server-side never rendered, so it got pressed four more times and answered `23505` four times. Patches now collect in `pendingPatches` (a ref) and flush in one pass at `PATCH_FLUSH_MS` (100ms). Three invariants: cost tracks **flushes, not events**; use a **timer, not `requestAnimationFrame`** (rAF stops in a background tab and uploads are what people background); and patches **merge, never replace**, or a progress tick drops a status set in the same window and `cancelBatch` then deletes a file that had already started. Diagnosis rule: read the **durable record** (Vercel route/status breakdown) before the code — `/api/upload` answering 200 fifty-two times while `/api/upload/[imageId]` never appeared located this on the client in one query.
- **A refusal is not a failure, and an `.in()` filter is URL length.** Rejected files (camera raw, PSD, HEIC, over-cap) carry status `incompatible` — amber, dismissible, **no Retry** (the validator would reject them again instantly); `uploadRejectionReason()` returns the BARE phrase because the row already prints the filename, while `validateUploadFile()` keeps the name prefix for the presign route, which reports on a whole batch. Separately: PostgREST puts `.in()` values in the query string, so an unbounded list returns a bare **400** — `check-duplicates` failed 36 times in 25 minutes this way, self-amplifying (its id list was every image in the section) and **invisible, because it reported via bare `console.error`**. Page every filter list, and never let a swallowed-by-design failure skip `reportSystemError`.
- **Upload rows are presign-created BEFORE their binary exists** — any new exit path from an upload session (cancel, unload, error) must clean its rows up or they become ghost tiles (lessons #21–23, the eBay incident). The client may only mark "complete" on a server-confirmed 2xx; `/api/upload/reconcile` truth-checks each batch; the Inngest `upload-reconciler` (nightly 2:43am PT + `reconciler/run` event) heals or deletes stragglers and emails a report.
- **Gallery passwords are event-level with write-through, and have exactly one write home:** `PUT /api/events/[eventId]/gallery-password`. It writes the plaintext to `events.settings.sharing.password` (owner-scoped JSONB — the photographer must be able to read it back, and the email composer must be able to print it) AND re-hashes into `password_hash` on every **active** share. Never write one side alone: the plaintext without the hashes is a gallery the owner thinks is locked, and the hashes without the plaintext breaks the email toggle. `POST /api/shares` inherits the event password unless the body explicitly supplies one — a posture, not a default (lesson 35).
- **The bulk download PIN gates the WHOLE GALLERY and nothing else** (2026-08-21, `src/lib/gallery/download-gate.ts`). A person's stack, a section, favorites, a picked selection, and a curated share link's "download all" are subsets, gated by `requirePinIndividual`. `authorizeShareDownload` derives the gate from the ZIP `scope` the route passes in; the gallery client imports the same pure function, so prompt and refusal cannot disagree. It used to be "any ZIP is bulk", which walled off "Download all 18" on one person's group (lesson 95).
- **The download PIN follows the SAME rule, and now has the same shape:** `PUT /api/events/[eventId]/download-pin` writes `events.settings.sharing.{downloadPin,requirePinBulk,requirePinIndividual}` AND all three columns on every **active** share, normalizing ONCE so the two can never disagree. It got only the event half until 2026-08-12, and since every consumer reads the SHARE (`authorizeShareDownload`, the gallery payload, the email composer), a gated gallery was served ungated and its PIN was omitted from the email announcing it. **`resolveSharePins()` (`src/types/event-settings.ts`) is the single home for what a NEW share inherits** — the trap was that inheritance was gated on `useEventDefaults`, which the email composer does not pass, so the one path that most needed it was the one that skipped it. A PIN on the event is a posture, like the password: it applies whether or not defaults were asked for. Never re-inline this at a call site; shares are minted from three places.
- **What a share exposes to a guest has exactly one resolver: `resolveShareImageScope()`** (`src/lib/gallery/share-scope.ts`). Every guest read path (gallery payload, cover, OG card, search, selfie-search, downloads, favorites writes) asks it, and it fails CLOSED — a `share_type` it doesn't know how to narrow serves nothing. `shareScopeIdFilter()` returns `null` only for a genuinely unrestricted share and an EMPTY set for a denied one, so a caller that forgets the 404 branch still shows nothing. Never re-inline `share_type === "selection"` at a call site; adding `section`/`person` shares means adding a case to that switch (lesson 55).
- **`database.types.ts` is GENERATED — never hand-edit it.** `npm run db:gen-types` (wrapper: `scripts/gen-types.sh`) generates to a temp path, sanity-checks line count + required symbols, then moves into place; it reads the access token from the `supabase-access-token` keychain item. The types check the **table name** and the **result Row shape** — they do NOT check `.eq()` filter columns, so a filter on a nonexistent column still compiles and fails at runtime as a 400 (lessons #49–51).
- **The share cover has ONE resolver: `resolveShareCoverUrl()` (`src/lib/cover/resolve-share-cover.ts`).** The durable email-hero redirect, the email composer's decision to attach a hero at all, and `EmailPreview` all go through it. A caller that re-derives "does this share have a cover" will drift from the route that answers it — that fork shipped a dead `<img>` in every email for 4 of 8 live selection shares. Internally it scopes through `resolveShareImageScope()` (the line above) — the two single-homes compose, they don't compete. E2E: `npx tsx scripts/verify-share-cover.ts <apiBase>`.
- **PostgREST's embedded `table(count)` is a per-row correlated subquery, and `images` is too hot for it.** The dashboard's "N images" came from `events.select("*, images(count)")`; because `images` is written to constantly, its visibility map is never current and that "index-only" scan does a heap fetch per row — 23,136 for 26 events. Warm 16ms, measured 2,641ms on a busy morning, and past the **8s `statement_timeout` PostgREST inherits from the `authenticator` role** it is cancelled outright (`service_role` has no `rolconfig` of its own, so it does NOT get an exemption). The count now rides `event_readiness` (migration 047), which aggregates the same rows in ONE grouped pass for the status badges anyway. Rule: **a count over a hot table belongs in a grouped aggregate you already run, never in an embed.** Corollary — **an enhancement must never be able to fail the page it decorates**: the list route runs its enrichment legs under `Promise.allSettled` and reports each failure, because for months a slow count returned a blank dashboard reading "Something went wrong" with no `system_errors` row and no admin email.
- **Vector search runs on FINGERPRINTS, not raw vectors** (migrations 050/051). `binary_quantize` reduces each embedding to one bit per dimension (144 bytes vs 4,608); the fingerprint index picks a shortlist by Hamming distance and the real vectors re-rank only those. 329 MB of index became 27 MB with 99.7% result overlap, because RAM is the only expensive resource here (~$13/GB/month as Supabase instance tiers, vs $0.125 disk and $0.015 R2) and at ~370k photos/year the old index reached 17 GB and a $410/month instance in four years. Three invariants: **`hnsw.ef_search` must be >= the shortlist size** or the index walk truncates silently (the first attempt returned 8 rows where 30 were asked for, and the OLD selfie search had been capped at 40 for months by the same default); **every filter belongs INSIDE the shortlist**, or a search scoped to one gallery shortlists other galleries and returns nothing; and **`score_images_by_embedding` must never get a shortlist** — it has no ORDER BY or LIMIT because it scores every photo in an event, so a shortlist would turn "score all" into "score some" behind the same name. Harness: `scripts/triage/search-ab.ts capture|compare`.
- **A Supabase error is a return value, not a throw** — `const { data } = await …` followed by `data || []` turns a 400 into a believable empty result. Check `result.error` on any query whose emptiness would look plausible. `shares`/`favorites`/`images` have no `user_id`; scope them via `.in("event_id", eventIds)` or an `events!inner(user_id)` join.
- **Sort is PER SECTION** (`sections.sort_mode`/`sort_seed`, migration 045; NULL inherits the event default). The editor's dropdown writes to the ACTIVE section — only "All Images" writes the event setting — and the guest gallery renders each tab in its own section's order. "random" is seeded SERVER-side so every client sees the same shuffle until it's deliberately reshuffled.
- **Archive card covers honor cover TYPE**, not a leftover `cover.imageId` (mosaic/color show their composed raster; photo fallbacks anchor on `focal_x/y`, preferring a frame that has one). Same class of bug as the email hero: a caller that re-derives what another surface decides will drift from it.
- **Event Intel is ONE STUDIO'S feature, gated by `hasIntelAccess()` (`src/lib/event-intel/access.ts`) — and the gate is an id list (`EVENT_INTEL_USER_IDS`), NOT `is_admin`.** Measured before choosing: every crew/venue/org/event row belongs to info@ (the shared team login) while `is_admin` is mason@'s only, so admin-gating inverts the answer. The calendar behind the create-screen autocomplete is one service account on hardcoded Two Dudes calendars — a studio resource, unlike `sps_connections` which is per-user and correctly open to everyone. Registry routes (`/api/crew`, `/api/venues`, `/api/organizations`, `/api/events/[id]/intel`, `suggest-gig`) gate via `getIntelUser()`, a drop-in for `getAuthUser()` — new intel routes must use it, and it does NOT replace the per-query `.eq("user_id")` filters (feature gate and ownership filter are different protections). Intel follows the EFFECTIVE user; Ops follows the REAL one (a power act-as must not lend; data belongs to the archive you are looking at). Fails closed: no env var, no Intel. When users someday connect their own calendars, the gate becomes "has a calendar connection" and only `hasIntelAccess()` changes (lesson 85).
- **"Last hired" is DERIVED, never stored** (migration 062, `src/lib/event-intel/last-hired.ts`). `crew.last_hired_on` holds only the hand-entered seed month; the value every surface shows is `max(seed, newest linked event date)`, computed on read. That is what makes "it updates any time they work an event" true by construction — confirming a gig on the create or import screen IS the update, and there is no stored copy to rot. Non-regulars only. Format is Mason's: `Aug 2024 (2 yrs)`, and under a year the AGE becomes `(Recent)` while the month still shows. `scripts/backfill-last-hired.ts` seeded 77 of 87 from twelve years of calendar (max-only, studio sittings and future dates excluded).
- **One segmented pill for every "pick exactly one"** (`src/components/ui/segmented.tsx`). Loose `rounded-full` chips read as independent toggles; one track with hairline dividers reads as a single question. Selection is the BRAND ACCENT, because emerald here means state (active axis, progress, selection rail) and a filter is a view you are in. The exception is why the component takes no colour prop: a group whose VALUES each carry meaning — the rehire ladder, stone → amber → red — is a statement about a person, not a view, and keeps its severity ramp. A flag (`lead`) and independently-confirmable chips are NOT segmented; that shape promises "exactly one".
- **`can_lead` and `travels` are GONE** (2026-08-15). Both duplicated something better: `can_lead` overlapped the per-gig `lead` role (who led is a fact; a standing "could lead" is a guess you maintain forever), and `travels` overlapped the radius search, with the flag unset on 35 of 61 people. The radius search's "Would travel" group went with it. **The columns are left dormant, unread and unwritten** — dropping is irreversible and they hold no traffic.
- **Archived crew are "Alumni" in the UI, `archived` in the data.** The word is Mason's for the /people wall ("maybe it's fun to see them") and now reads the same on the Roster. Every band filter — Crew axis, Roster, /people wall — offers All · Regulars · Non-regulars · Alumni, defaults to All, and NARROWS SEARCH rather than being bypassed by it. **"All" means ALL, alumni included** — it briefly meant "all active", which put a hole in the search that nothing on screen explained (lesson 91). The tell: the bands sum to the CREW tab's total, so All cannot be a subset.
- **Crew faces (`tasks/crew-faces.md`, migration 061): crew identity NEVER touches `persons.name`** — that is guest identity space (People index, wall of fame, guest selfie search), and naming staff into a client's clusters is one future feature away from a share. `crew_persons` links clusters; `crew_faces` holds reference SETS with snapshotted embeddings (deleting the setup frame must not un-teach recognition); `is_avatar` is the pin, one per person by partial unique index. Matching is `findCrewInArchive()` — the selfie engine pointed at references; AI suggests, a human's confirm writes AND teaches (the cluster's representative face joins the set). ⚠️ **Any PostgREST embed through `images`↔`events` needs the FK hint** (`events!images_event_id_fkey!inner(...)`) — the tables are related twice (event_id up, cover_image_id back) and an unhinted path fails outright, which hid inside a best-effort catch on the first live confirm (lesson 86). Best-effort means the outcome is optional, never the evidence: report swallowed failures to `system_errors`.
- **Event Intel (`/intel`) is the back-office pivot — INTERNAL, never a guest surface** (built 2026-08-13; full doc `tasks/event-intel.md`). ONE fact table (the event, plus venue/crew/orgs) read along four axes, which is why a person's venues and a venue's crew can never disagree — they are the same pass (`buildIntelIndex()`, `src/lib/event-intel/index-intel.ts`). It holds venue logistics, client structure and **rebook judgements about named people who do not work here**; there is no share path to it and there must never be one. Three invariants learned from real data: **identity and label are separate for organisations** exactly as they are for crew — the domain keys the row, `orgDisplayName()` takes the NAME from Mason's own gig titles (domain stems gave "Collegeboard", "Ebay", "Getclario Ai"); **"where" has one vocabulary**, `metroKeys()` in `geo.ts`, because venues carry Google cities (San Jose, Coppell) and crew carry roster shorthand ("Bay Area", "SLC", "Seattle/LV/NYC") and comparing raw strings returned zero local crew for all 47 cities; and **an empty dimension is explained, never hidden** — roles are 0 of 42 links and the panel says why. Fixture playground at `/dev/intel`.
- **`/dev/*` is DEV-ONLY, gated on `NODE_ENV === "development"`** (fixed 2026-08-13 — it was unconditionally public and `app.pixeltrunk.com/dev/buttons` answered 200 to anyone). Never write this as `VERCEL_ENV !== "production"`: it reads as the same rule and fails OPEN, since any non-Vercel runtime satisfies it. A playground is exactly where someone renders real data to look at it.
- **People index (`/people`)** is archive-wide and INTERNAL; identity comes from `personNameFromParts` (never re-derive names) — full doc in `docs/OPS.md`. Membership asks TWO questions, each single-homed and both read by the index count, the spotlight payload, and the `?person=` deep link: **`personKeyForImage()`** = whose SHOOT this frame is (filename), and **`loadFaceMembership()`** (`src/lib/people/face-membership.ts`) = who is IN it (named face clusters), which is what puts group shots on a card. A person's card means "photos they are in", so **one group shot appearing on several cards is correct** — Mason: *"THAT IS THE POINT."* Identity from a URL still gets `looksLikePersonName` first; clicking a face opens the spotlight — never a bare link into an event, which is how "77 photos" became a 5,787-image event filtered to nothing. Face membership DROPS any cluster claiming 2+ faces in one photo (contamination — a person appears once per frame; Steven Hughes's cluster holds 203 faces across 184 photos), never heroes a group shot, and admits only vouched identities. Full doc + what's not built: `tasks/people-group-shots.md`.
- **The identity engine (2026-08-16, full doc `tasks/people-group-shots.md`): AI suggests, a human's word is durable, crew outrank filenames.** `person_identity_suggestions` (migrations 065–069) matches anonymous face clusters against reference centroids at a **measured 0.55 floor** (impostor max 0.363, true-match median 0.886 — recalibrate before changing). Scan order is CREW FIRST (`match_person_cluster_to_crew` over `crew_faces`; crew barely exist in filenames — Mason is the only crew member with a filename identity), and **a crew confirm is a `crew_persons` LINK via `confirmCrewPerson`, never a `persons.name` write**. A guest confirm writes `persons.name` (human-authored, so consensus never overwrites) and refreshes that event's centroids — teach-on-confirm. A reject (or a human clearing a name — migration 063) lands in `persons.rejected_names` and is NEVER re-asked or auto-refilled; `nameIsRejected()` compares letters-only so spellings stay rejected. Identity merges live in `person_aliases` (064): one resolver (`src/lib/people/aliases.ts`) folds alias keys at EVERY identity decision point — index, face membership, detail, `?person=` deep link — because a subset folding is the tile/card drift of lesson 88. The reference refresh takes the excluded-gallery list as a param (068) — the marketing galleries mint fake people, and "Golden Gate YPO" was reference material until it did. Full centroid rebuilds exceed PostgREST's 8s budget: event-scoped refresh routinely, full seed via `scripts/db-sql.ts` (lesson 93).
- **Face suggestions: a GROUP SHOT is never evidence of who a face is** (lesson 96, 2026-08-21). Mislabels AND splits seed from solo frames only (`faceCountByImage` is on the call for exactly this; group files are named for whoever booked them — "Justin Group"); and two same-name clusters that share a frame are never offered a merge, because a person appears once per photo (the 5-face "Kaitlin Kinzer" cluster was her dog). Any new suggestion type gets both rules before it ships.
- **Every paged read (`.range()`) MUST carry `.order()` on a unique column, and concurrent paging must dedupe by row id** (lesson 88). `range()` is OFFSET/LIMIT and Postgres defines no row order without an ORDER BY — its *synchronized sequential scans* start a new scan wherever a concurrent one already is, so N parallel pages each see the table differently, overlapping and leaving gaps. `/people` read **64 photos for a 35-photo shoot** this way. Measured: an unordered control corrupted **4 of 8 runs**, duplicating up to 10,202 rows. Regression harness `scripts/triage/verify-people-counts.ts` runs the UNORDERED shape alongside the fixed one *on purpose* — a single clean run of a nondeterministic bug is not evidence. Related: an unpaged PostgREST select silently caps at **1,000 rows**, and a truncated read is indistinguishable from a real absence.
- **The guest gallery and the owner's preview are ONE component** (`src/components/gallery/GalleryExperience.tsx`), rendered by `/gallery/[slug]` and `/gallery/preview/[eventId]`. They differ only by `apiBase` and a four-flag `capabilities` object (favorites / tracking / passwordGate / downloads). Never fork them again — the 609-line preview copy had silently drifted to filename-only search with no selfie search, so a preview answered "is this what my client sees?" with a confident wrong yes (lesson 70). Selfie MATCHING likewise has one home, `matchSelfie()` (`src/lib/faces/selfie-match.ts`), shared by both search routes.
- **The OWNER's own view is not a view.** `share_views` / `activity_log.share_view` are what `src/lib/events/status.ts` reads as DELIVERY EVIDENCE — a gallery is "opened" because someone looked, not because an email was sent. So `/api/gallery/[slug]` skips both the counter and the log when `getOptionalUserId()` matches `events.user_id`. This became load-bearing when the event page grew a **View** button pointing at the real share (published events show View → `/gallery/<slug>`; unpublished still show Preview → the owner route). `getOptionalUserId()` exists because `getAuthUser()` 401s an anonymous caller, which is fatal on a guest route — "who is asking" and "is the caller allowed" are different questions.
- **Crew judgements use the REHIRE LADDER, and its rules live in `src/lib/event-intel/roles.ts`** — `first_call | solid | last_resort | never` (ordinal, best-to-worst). Four invariants, each learned from use: a standing is the **most recent** judgement, never an average (a mean buries one disastrous gig under four fine ones); it is **hidden on the event being rated** until that event has its own rating (`standingVisibleFor`), because seeing "First call x4" while rating is an invitation to agree with yourself; a **hard no sinks** in every picker via `compareCrewForPicker()` but is never removed; and `crew.rehire` is a person-level **baseline** that any real per-gig rating outranks. Regulars are not rated and are not asked their discipline, whether they can lead, or whether they travel — all implied, resolved ONLY through `canLead()` / `willTravel()` (verified: 15 regulars, all photographers).
- **Gallery status is TWO independent axes** (`src/lib/events/status.ts`): a delivery ladder (draft → published → sent → opened → downloaded) and pipeline readiness (uploading / indexing). They must never merge — a gallery is routinely sent while its AI processing is still queued. Delivery evidence is a VIEW, not an email: 6 of 15 live galleries were opened without an email ever leaving Pixeltrunk, so "we sent an email" is not the definition of shared.
- **A stale `pending` row blocks an event's entire AI pipeline.** `countPendingUploads()` only counts rows younger than `PENDING_UPLOAD_STALE_MINUTES` (30) — before that gate, nine ghost rows out of 5,787 kept `ai-index` returning `skipped: "uploads-in-flight"` forever, which also meant `faces/cluster.requested` never fired. "Dismiss" on the stalled-uploads banner now `DELETE`s those rows for real (HEAD in R2 first; rows whose bytes landed are left for the reconciler) — it used to write a localStorage flag and nothing else (lesson 67).
- **There is NO HTML sanitiser in the email path, and `normalizeBodyForEmail()` is the only place body HTML is touched.** TipTap → `interpolateTemplate` → `/api/emails/send` → `renderEmailShell` passes the composer's HTML through byte-identical. Blank lines still vanished, because an empty `<p></p>` measures 0px and collapses its margins into its siblings — a rendering bug, not a stripping one (probe: `/dev/email-html`, which prints the HTML at each stage). `EmailPreview` imports the same normalizer; never inline a variant, or the preview goes back to lying about the email being sent.
- **The guest-list spreadsheet is EMAIL-RECIPIENT ONLY** (`src/lib/guest-list/store.ts`). The SPS analytics export attached to an event is reachable solely via `/api/guest-list/[token]` — never the gallery, never a share slug, never a guest nav. It is PII (guest names, emails, sign-in answers): the token is 32 bytes stored as a SHA-256 hash, rate-limited, requires a LIVE share (410 otherwise), and every download is logged. The route is on the middleware's PUBLIC list ON PURPOSE — the token is the authorisation and the recipient is a client with no account (lesson 72). SPS exports **XLSX**, not CSV.
- **Selfie search is ON by default** (2026-08-10) and read ONLY through `selfieSearchEnabled()` — absent means enabled, explicit `false` is the opt-out. Events store `{}` and all sharing defaults resolve at read time, so a `=== true` check silently pins every existing event to the OLD default; that's the trap for any future default flip in `SharingSettings`.
- **Alpha ops invariants (full doc: `docs/OPS.md`):** signup is table-gated (`allowed_signups`) with public Supabase signups disabled at the project level; `is_admin` belongs ONLY to mason@ (never the shared info@ team login); admin gates check `realUser` (act-as can't leak /ops); every /ops PAGE awaits `assertAdminPage()` BEFORE fetching — a layout is not a security boundary under streaming SSR, and access control is verified with raw curl. `recordUsage()` is always awaited; prices exist only in `src/lib/usage/costs.ts`; per-user cost math only via `getUsageOverview()`.
- **API catch blocks call `reportSystemError(context, err, detail)`** (`src/lib/monitoring/report.ts`) — never bare `console.error` alone. It writes a queryable `system_errors` row + throttled admin email (needs `ADMIN_ALERT_EMAIL`, set in Vercel, NOT in local .env).
