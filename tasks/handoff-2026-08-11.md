## 1. NEXT UP: the download PIN has no write-through (confirmed live bug)

**Do this first.** One live client gallery is currently unprotected.

The PIN is stored on the EVENT (`events.settings.sharing.downloadPin`,
`requirePinBulk`, `requirePinIndividual`) and never copied to the SHARE row.
Both consumers read the share, so both silently see "no PIN":

- `src/app/api/gallery/[slug]/route.ts:481` → `share.require_pin_bulk` →
  **the guest is never asked for the PIN**
- `src/app/api/emails/send/route.ts:150` → `shareRow.download_pin` → **the PIN
  is omitted from the email** (this is the symptom Mason reported)

This is the exact failure shape CLAUDE.md documents for the gallery password:
*"Never write one side alone."* The password got a single write home with
write-through to every active share (`PUT /api/events/[eventId]/gallery-password`).
The PIN only ever got the event half.

**Both halves are independently proven** (and neither is Mason's own recent edit
— he asked, correctly, whether I was just seeing his change):

| event | share created | event settings updated | share state |
| --- | --- | --- | --- |
| FM Headshots // Jul 2026 | 2026-07-17 | 2026-08-10 | `download_pin=null`, `require_bulk=false` |
| Island HQ Headshot Day | 2026-08-12 04:51 | 04:51 had `requirePinBulk=true` | `download_pin=null` |

- FM proves **existing shares are not updated** when the PIN is turned on later.
  Untouched by Mason; `/gallery/goFTQbVX33` is live and unenforced.
- Island HQ proves **new shares do not inherit** the PIN: the share was created
  at 04:51 while the event still had `requirePinBulk: true`, and still got null.
  (Mason turned the flag off at 05:03 after sending without a PIN.)

**The fix, in the shape the password already uses:**

1. One write home for PIN changes: writes the event JSONB **and**
   `download_pin` / `require_pin_bulk` / `require_pin_individual` on every
   ACTIVE share.
2. `POST /api/shares` inherits the event's PIN, the way it already inherits the
   password.
3. Backfill the one mismatched live share — **ask Mason first**: it flips an
   already-delivered gallery from open to PIN-gated. Correct state, visible
   change.
4. `setIncludePin` in `src/app/events/[eventId]/share/page.tsx:67` is declared
   and NEVER called — there is no toggle. `includePin` is hardcoded `true` and
   posted. Wire it to a real control (the neighbouring `includePassword` at
   line 485 is the pattern).

Diagnostic scripts: `scripts/triage/pin-gap.ts`, `pin-timeline.ts`.

## Process lessons worth not repeating

- **Lesson 84** (in `tasks/lessons.md`): a repro that does not reproduce is an
  untested instrument, not evidence. I diagnosed the date picker correctly,
  built a repro, it failed to reproduce, and I reverted a CORRECT fix. The repro
  was broken three ways — `.next` corrupted by iCloud so the page had zero
  stylesheets, animations throttled in the headless pane, and the hit-test
  probed outside the overlap region.
- **Unchecked Supabase errors bit twice tonight**, once on the live-event gate
  (a bad `events!inner(name)` join returned "no activity" while 785 rows sat in
  the window) and once on a shares query with a nonexistent `updated_at` column.
  Check `error` on ANY query whose emptiness would look plausible.
- **`.next` corrupts from iCloud sync repeatedly** (`static/css 2`, `BUILD_ID 2`).
  Cost a phantom debugging session. Worth a local-only `distDir` outside the
  synced tree.
- **Two sessions commit to this checkout.** `git push origin main` shipped six
  commits when I expected three, and the other session force-pushed a rebase
  mid-session. Always `git log --oneline origin/main..HEAD` as its OWN command
  and read every line before pushing.
